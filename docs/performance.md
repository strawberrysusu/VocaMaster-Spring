# 성능 실측 — Redis 랭킹 전/후 (Phase 7 ⑧)

> 1차 측정(8/27)은 **웜/콜드 불공정 비교로 판명되어 철회**하고, 8/28 공정 재측정으로 교체했다.
> 이 문서는 "캐시를 붙였더니 빨라졌다"가 아니라 **"측정을 검산했더니 결론이 뒤집혔다"**의 기록이다.

## 측정 대상

**공개 덱 인기 정렬** `GET /public/decks?sort=popular` — 같은 엔드포인트를 두 경로로:

- **Redis ON**: ZSET 랭킹에서 순서 조회 → DB가 내용·공개 권한 재검증 (ADR-034·038)
- **Redis OFF** (`ranking.popular.enabled=false`): DB가 매 요청 `like×5+copy×3+study×1` 계산 + 정렬

## 1차 측정 (8/27, 철회) — 무엇이 틀렸나

한국→도쿄 외부 경로, `stages` 워밍업 15초 + 측정 45초, 조건당 1회:

| | ON | OFF | 겉보기 |
|---|---|---|---|
| p95 | 112.6ms | 399.5ms | "3.5×" |
| p99 | 175.2ms | 698.5ms | "4.0×" |

**철회 사유** (Codex 교차 검산 + 재측정으로 확인):

1. **웜 vs 콜드 불공정** — ON은 오래 떠 있던 웜 JVM, OFF는 `ranking-off` 전환 **재기동 직후 콜드 JVM**에서 측정했다. 1/8코어 버스터블 CPU에서 JIT 워밍업은 분 단위로 걸리는데(재측정에서 p50이 97→64→12ms로 3분에 걸쳐 하강하는 것으로 실증) 15초 워밍업으로는 태부족. **OFF의 399ms는 DB가 느려서가 아니라 JVM이 덜 풀려서였다.**
2. 워밍업 15초를 "수치 제외"라고 적었으나 실제로는 k6 기본 요약에 **포함**되어 있었다 (stages는 라벨일 뿐 집계를 나누지 않는다).
3. 조건당 1회 측정 — 우연 변동 배제 불가.
4. 한국→도쿄 외부 경로는 시간대에 따라 왕복 지연이 수백 ms까지 출렁여(8/28 저녁 재현: 동일 조건에서 p95가 105~497ms로 요동) 서버 처리 차이(수십 ms)를 삼킨다.

## 2차 공정 측정 (8/28) — 방법

- **서버 내부**(`127.0.0.1:8080`)에서 k6 실행 — 네트워크 잡음 제거, 순수 앱+저장소 경로
- **워밍업 분리**: 30초 워밍업 실행 후 결과 폐기, 본 측정 60초 (코드로 보장 — [`popular-steady.js`](../tools/k6/popular-steady.js), stages 없음)
- **조건당 3회 반복**, VU 10, 원시 결과 전량 보존 ([`tools/k6/results/`](../tools/k6/results/))
- OFF 전환은 레포의 [`deploy/ranking-off.yml`](../deploy/ranking-off.yml) override로 재현 가능

## 2차 결과 — 결론이 뒤집혔다

| run | ON p50 | ON p95 | OFF p50 | OFF p95 |
|---|---:|---:|---:|---:|
| 1 | 97.2 | 290.0 | 9.4 | 90.0 |
| 2 | 63.9 | 321.9 | 8.9 | 86.4 |
| 3 | 12.3 | 120.3 | 8.5 | 80.9 |

(ON run1~2의 p50 하강 곡선은 재기동 후 JIT 워밍업 잔여 — run3이 정상 상태에 가장 가깝다. OFF는 3회 모두 안정.)

**현재 데이터 규모(PUBLIC 덱 수 개)에서는 Redis OFF(DB 직접 정렬)가 더 빠르고 안정적이다.**
정상 상태 기준 p50 9 vs 12ms, p95 81 vs 120ms — ON 경로는 원격 Redis 왕복 2회(ready 확인 + ZREVRANGE)가
순이익 없이 얹히고, 결국 내용·권한 검증으로 DB도 다시 가기 때문이다. 정렬할 행이 몇 개뿐이면
"미리 정렬해둔 값"의 절약분이 왕복 비용보다 작다.

## 그럼 Redis 랭킹은 실패인가? — 아니다, 규모의 문제다

- DB 경로 비용은 공개 덱 수 N에 대해 **매 요청 O(N) 점수 계산 + 정렬**로 자란다.
  ZSET 경로는 조회가 O(log N + 페이지 크기)로 완만하고, 재구축(1시간 TTL)만 O(N)이다.
  **N이 커질수록 역전이 예정된 구조**이며, 현 규모에서는 그 교차점 왼쪽에 있을 뿐이다 (교차점 실측은 미완 — 합성 데이터 부하가 후속 후보).
- fail-open 설계(Redis 장애 시 DB 폴백)라 **캐시를 켜두는 비용이 장애 위험으로 전환되지 않는다** —
  이번 검증 과정에서 실제로 Redis를 껐다 켜도 서비스는 무중단이었다.
- 즉 현재 상태는 "성능을 위해서"가 아니라 **"성장을 대비한 구조를 무해하게 미리 깔아둔 것"**이 정직한 서술이다.

## 이번 검산에서 배운 것 (면접에서 말할 실전 교훈)

1. **JVM 앞에서 콜드/웜을 안 가르면 어떤 비교도 무효다** — 특히 저사양 CPU에서 JIT는 분 단위.
2. **1회 측정은 측정이 아니다** — 3회 반복의 분산(OFF: 81~90 안정 vs ON: 120~322 요동)이 신뢰도 자체를 알려준다.
3. **k6 VU 방식은 closed model** — 빠른 쪽이 같은 시간에 더 많은 요청을 처리하므로(1차에서 1,434 vs 1,231) 고정 RPS 비교가 아니다. 같은 도착률 비교가 목적이면 `constant-arrival-rate`.
4. **외부 경로 측정은 회선 상태가 신호를 삼킬 수 있다** — 비교 실험은 내부에서, 사용자 체감은 외부에서, 목적을 분리.
5. **진단은 기억이 아니라 설정 실값으로** — 이번 검증 중 잘못 기억한 IP·키 이름으로 "장애"를 오진할 뻔했다. 실값(`docker inspect`, 코드의 상수)에서 출발해야 한다.
