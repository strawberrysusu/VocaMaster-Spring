## 왜 손댔나 (한 문장)

**"카드 넘겼는데 답을 잘못 눌렀다. 되돌아가서 고치고 싶다."**

이게 UI 문제인 줄 알았는데 아니었다. **저장하는 시점**의 문제였다.

## 문제의 뿌리 — 왜 되돌릴 수 없었나

기존 구조는 이랬다.

```
알아요 누름  →  즉시 서버에 저장  →  Leitner 박스가 움직임
```

그런데 "몰라요"를 누르면 박스가 **1로 완전히 리셋**된다. 박스 4에 있던 카드가 1로 떨어지면서
`correctStreak`(연속 정답 수)도 0이 된다. **원래 4였다는 사실이 어디에도 안 남는다.**

그래서 "되돌리기"를 만들려면 사라진 값을 복원해야 하는데, 복원할 재료가 없다.

Quizlet은 왜 되돌리기가 쉬울까? 거기선 그 화면의 안다/모른다가 **세션 안에서만 사는 값**이기 때문이다.
우리는 그 버튼이 곧바로 영구 상태를 바꾼다.

### 바꾼 방법

```
세션 중  →  답을 브라우저 메모리에만 저장 (서버 안 감)
완료 누름  →  전체 답안을 한 번에 전송  →  이때 처음 박스가 움직임
```

이렇게 하니 **"되돌리기"라는 개념 자체가 필요 없어졌다.** 아직 저장 안 했으니 그냥 고치면 된다.
문제를 푼 게 아니라 **문제가 생기지 않는 구조로 옮긴 것**이다.

> 💡 이게 오늘 배운 것 중 가장 값진 사고방식이다. "되돌리기 기능을 어떻게 만들지"가 아니라
> "되돌릴 일이 없게 하려면 어디를 바꿔야 하지"를 물었다.

## 개념 4개 — 초심자용 설명

### 1. 트랜잭션 — 전부 성공 아니면 전부 취소

카드 200장을 한 번에 저장하는데 150번째에서 에러가 났다고 하자.

트랜잭션이 없으면 **149장은 저장되고 51장은 안 된 반쪽 상태**가 된다. 사용자는 뭐가 저장됐는지 모른다.

트랜잭션은 "이 묶음은 전부 되거나 전부 안 되거나"를 DB가 보장해주는 것이다.
Java에서는 메서드 위에 `@Transactional`만 붙이면 된다.

```java
@Transactional                       // ← 이 안에서 뭐가 터지면 전부 없던 일이 됨
public BatchAnswerResponse recordAnswers(...) {
    for (카드 : 답안들) { 박스 옮기기 }
    통계 갱신
}
```

**은행 송금**을 떠올리면 쉽다. "내 계좌에서 빠짐" + "상대 계좌에 들어감"이 반드시 같이 일어나야 한다.
하나만 되면 돈이 사라진다.

### 2. 멱등성 — 몇 번을 보내도 결과는 한 번

네트워크는 믿을 게 못 된다. 이런 일이 실제로 일어난다.

```
클라이언트 → 서버   요청 도착함, 서버가 처리 완료
클라이언트 ← 서버   응답이 오다가 유실됨
클라이언트          "실패했나 보다" → 다시 보냄
서버                또 처리함 → 박스가 두 번 올라감 ❌
```

클라이언트는 **"서버가 처리했는데 응답만 못 받은 것"**과 **"서버에 도달도 못 한 것"**을 구분할 수 없다.
겉보기가 똑같기 때문이다.

그래서 요청마다 고유한 **제출 ID**를 붙인다.

```
1차: submissionId=abc123, 카드 3장  →  서버가 처리 + "abc123 처리함" 기록
2차: submissionId=abc123, 카드 3장  →  서버가 기록을 보고 "이미 했음" → 아무것도 안 함
```

DB에 `(user_id, submission_id) UNIQUE` 제약을 걸면 이게 **최종 보증**이 된다.
프론트에서 버튼을 비활성화하는 것만으로는 부족하다 — 그건 우회할 수 있고, 네트워크 재시도는 막을 수 없다.

> ⚠️ 오늘의 함정: 같은 트랜잭션 안에서 UNIQUE 위반을 예외로 잡으면 안 된다.
> 그 순간 트랜잭션이 "롤백 예정"으로 표시돼서 뒤이은 조회가 못 나간다.
> 대신 `INSERT IGNORE`를 써서 **반환값 0으로 중복을 안다.** 예외가 아니라 숫자로 판단한다.

### 3. payload 동결 — 오늘 가장 크게 틀린 것

멱등성을 만들어놓고도 구멍이 있었다. 이런 순서였다.

```
1. 3장 답하고 제출  →  서버는 저장했는데 응답 유실
2. 새로고침
3. 4번째 카드까지 답함
4. 다시 제출  →  이번엔 4장을 보냄
```

**제출 ID는 같은데 내용이 다르다.** 서버 입장에선 "같은 ID로 다른 답안이 왔다"가 된다.

내가 처음 낸 답은 "새 ID를 발급해서 4장 전부 다시 보내자"였다. 근거는 이랬다.

> "클라이언트는 앞선 제출에 어떤 카드가 들어 있었는지 알 방법이 없다"

**이 전제가 틀렸다.** payload를 만든 게 클라이언트다. **보내기 직전에 그걸 저장해두면 된다.**

```
answers    = 지금 자유롭게 고치는 답안
attempted  = 실제로 보낸 순간 얼어붙은 답안  ← 이게 핵심
```

그래서 이렇게 바꿨다.

```
제출 버튼 클릭
  → ① 현재 답안을 attempted로 sessionStorage에 저장   ← 네트워크보다 먼저!
  → ② 그 attempted를 서버로 전송
  → 실패하면 편집을 막고, 같은 ID + 같은 attempted만 재시도
```

**①과 ②의 순서가 전부다.** 뒤바뀌면 응답 유실 시 "내가 뭘 보냈는지"를 잃는다.

실측으로 확인한 차이:

| | 동결 전 | 동결 후 |
|---|---|---|
| 이미 반영된 카드 3장 | box 2 → **3** (두 번 세어짐) | **box 2 유지** |
| `correctStreak` | 1 → **2** | **1 유지** |

> 💡 "감수할 수밖에 없는 한계"라고 생각한 게 사실은 그냥 내 설계 누락이었다.
> **"어쩔 수 없다"고 결론 내리기 전에 전제를 의심해봐야 한다.**

### 4. 400과 401은 다르다

비밀번호 변경에서 "현재 비밀번호가 틀렸다"를 **401**로 던지고 있었다.

문제는 프론트의 공용 API 함수가 이렇게 생겼다는 것이다.

```
401을 받으면  →  "토큰이 만료됐구나"  →  토큰 갱신  →  같은 요청 재시도
```

**비밀번호를 틀렸을 뿐인데 토큰 갱신이 돌았다.**

- **401 Unauthorized** = "너 누군지 모르겠다" (로그인 안 됨, 토큰 만료·위조)
- **400 Bad Request** = "너는 알겠는데, 보낸 값이 틀렸다"

이미 로그인한 사람이 비밀번호를 잘못 친 건 **명백히 400**이다.
상태 코드는 장식이 아니라 **클라이언트가 기계적으로 읽는 계약**이다.

## 오늘 실제로 터진 사고 6건

발견 순서대로. 전부 "돌려보지 않았으면 몰랐을" 것들이다.

### ① CSS 클래스 이름 충돌

새로 만든 별표 버튼에 `star-btn`을 썼는데, 그 이름이 **이미 덱 상세 화면의 30×30 아이콘 버튼**에 쓰이고 있었다.
그쪽 규칙이 파일 뒤쪽에 있어서 이겼고, 버튼이 30px로 눌려 **글자가 세로로 쪼개졌다.**

배운 것: CSS는 전역이다. 새 클래스명을 만들 땐 이미 있는지 먼저 찾아봐야 한다.

### ② `CHAR(36)` vs `VARCHAR(36)`

마이그레이션에 `CHAR(36)`으로 썼는데 Hibernate가 `VARCHAR(36)`을 기대해서 **앱이 아예 부팅을 거부**했다.

배운 것: JPA는 시작할 때 "내가 아는 스키마"와 "실제 DB"를 대조한다(`ddl-auto: validate`).
어긋나면 죽는다. 죽는 게 맞다 — 조용히 돌다가 나중에 터지는 것보다 훨씬 낫다.

### ③ 프론트를 빌드해도 서버가 옛것을 준다

React를 다시 빌드했는데 화면이 안 바뀌었다.
Spring이 **기동 시점의 정적 파일**을 서빙하고 있어서, 서버를 재시작해야 새 파일이 나갔다.

배운 것: "빌드했으니 반영됐겠지"는 추측이다. 실제로 바뀐 화면을 봐야 확인이다.

### ④ 지운 초안이 되살아났다

제출 성공 후 `sessionStorage`를 지웠는데 다시 살아났다.
React의 자동저장 `useEffect`가 상태 변화에 반응해서 **방금 지운 걸 다시 써버린** 것이다.

배운 것: React에서 "지우기"와 "자동저장"이 같이 있으면 순서를 반드시 확인해야 한다.

### ⑤ merge했는데 배포가 안 됐다 — 제일 무서운 것

PR을 merge했고, CI가 초록이었고, 다 끝난 줄 알았다.
그런데 서버 컨테이너가 **56분째 그대로**였다.

확인해보니 **merge 커밋에 대한 CI 실행이 아예 생성되지 않았다.**

```
head_sha=b4e3827  →  run 0건, check-run 0건
```

skip 마커도 없고 Actions도 켜져 있었다. **원인은 아직 모른다.** 빈 커밋을 하나 밀어서 해결했다.

배운 것 (이게 오늘 제일 실무적인 교훈):

> **"CI가 성공했다"와 "배포됐다"는 다른 말이다.**
> merge 후에는 **운영 서버가 실제로 새 버전인지**를 직접 확인해야 한다.
> 컨테이너 기동 시각, 배포된 파일 안의 새 문구, 이런 걸 눈으로 봐야 한다.

그리고 이때 `workflow_dispatch`(수동 실행)가 설정돼 있지 않아서 버튼 하나로 재배포할 방법이 없었다.
**다음에 CI를 손볼 때 세 개를 한 세트로** 해야 한다.

- `workflow_dispatch` 트리거 추가
- deploy 조건이 `event_name == 'push'`라서 그것도 같이 풀어야 함
- **운영 중인 커밋 SHA를 확인하는 장치** ← 이게 있었으면 즉시 알았다

### ⑥ "백엔드만 있고 화면 없는 것" 조사를 두 번 틀렸다

"더 없다"고 두 번 말했는데 두 번 다 틀렸다.

**첫 번째 실수 — 경로만 봤다.** `DELETE /users/me`를 프론트가 호출하니까
`PATCH /users/me`(닉네임 변경)도 "사용 중"으로 잡혔다. **HTTP 메서드를 안 봤다.**

**두 번째 실수 — DTO 필드를 안 봤다.** 엔드포인트 단위로만 봐서,
서버가 내려주는데 화면이 안 그리는 필드는 아예 시야 밖이었다.

제대로 6개 관점으로 다시 돌리니 **26건**이 나왔다.

배운 것: **"조사했더니 없었다"는 조사 방법이 촘촘했을 때만 의미가 있다.**
없다고 말하기 전에 "내가 어떤 각도로 봤지?"를 먼저 물어야 한다.

## 코드와 문서가 어긋나면 둘 다 거짓말이다

오늘 세 군데를 잡았다.

| 어디 | 뭐라고 써 있었나 | 실제 |
|---|---|---|
| `@Operation` (Swagger) | "모든 세션 강제 로그아웃" | refresh 토큰만 폐기. **access 토큰은 1시간 유효** |
| 화면 안내 문구 | "모든 기기에서 즉시 로그아웃" | 같음 |
| `UserService` Javadoc | "즉시 강제 재로그인" | 같음 (아직 안 고침 — 백로그) |

셋 다 **동작은 멀쩡한데 설명이 거짓말**이었다. 이게 더 위험하다.
코드가 틀리면 테스트가 잡지만, 문서가 틀리면 아무도 안 잡는다.
그리고 그걸 읽은 사람이 잘못된 보증을 믿는다.

**반대 방향도 있다.** `privacy.html`에 "탈퇴 시 공개한 단어장도 노출되지 않습니다"라고 써 있었는데,
확인해보니 코드가 실제로 5개 조회 경로 전부에서 걸러내고 있었다. **약속을 지키고 있었다.**
문서를 쓸 때 코드를 보고 썼다는 뜻이다.

## 면접 대본

### 30초 답변

> 카드 답변을 누를 때마다 진행도를 즉시 변경해서 이전 답을 수정하기 어려웠습니다.
> 세션 중에는 답을 브라우저의 임시 상태로 관리하고, 완료할 때 최종 답안만 일괄 제출하도록 바꿨습니다.
> 서버에서는 하나의 트랜잭션으로 전체를 반영해 부분 저장을 막았고,
> 제출 ID의 유일성 제약으로 더블클릭이나 네트워크 재시도에도 중복 반영되지 않게 했습니다.

### 꼬리질문 4개

| 질문 | 답 |
|---|---|
| 왜 트랜잭션? | 중간 카드가 실패하면 반쪽만 저장된다 |
| 왜 제출 ID? | 응답이 유실돼 재시도해도 박스가 두 번 안 움직이게 |
| payload 해시는 왜? | 같은 ID인데 내용이 바뀌면 조용히 무시하지 않고 409로 거절 |
| 왜 이벤트를 커밋 후에? | 롤백된 학습이 통계·캐시에 반영되면 안 되니까 |

### "그 설계가 실제로 도움 된 적 있냐"

> 운영에서 테스트하다 실수로 제출 버튼을 눌렀습니다.
> 영수증 테이블에 답변 수가 남아 있어서 몇 개가 반영됐는지 추측 없이 알 수 있었고,
> 통계를 정확히 되돌렸습니다.
