## 이해한 것

### 1. Redis가 뭔가 — 그리고 "HashMap으로 되잖아요?" 반박

> 시작 문장: "Redis는 메모리에 키-값을 저장하는 별도 서버다. HashMap이 더 빠른데도 쓰는 이유는, 서버가 2대가 되면..."
> ✍️ (숫자 그림 포함: 공격 5회 → A서버 3회, B서버 2회 → ?)
서버가 집계를 하긴 하는데 각각 집계를 하고, 동시에 그 집계 숫자를 카운트하지 못해서 조건에 만족하지 않아 공격당할 수도 있다. INCR은 레디스에서 쓰는 원자적 업데이트라고 생각하면 되겠네.
*(막히면: ADR-034. 키워드: 공유 카운터, 재시작 초기화, TTL 공짜, INCR 원자성)*

### 2. 캐시는 순서만, 권한은 DB — 이번 Phase의 제1원칙

> 시작 문장: "쿠키를 믿지 않듯 캐시도 믿지 않는다. ZSET에는 ___만 넣고..."
> ✍️ (비공개로 바뀐 덱이 캐시에 남아도 노출 안 되는 이유까지)
캐시에 순번 id 만 매겨서 정렬 최종검증은 마지막에 db 가 하기 때문에 
*(막히면: ADR-035, cache-strategy.md)*

### 3. 랭킹 점수는 왜 커밋 확정 후(afterCommit)에만 올리나

> 시작 문장: "더블탭 두 번째 요청이 unique에 걸려 롤백되면, DB는 되돌아가는데 Redis에 올린 +5는..."
> ✍️ (+ 놓친 갱신은 뭐가 수습하나 — 최종적 일관성이라는 단어까지)
마지막에 롤백되면 홀로 남은 redis 찌꺼기 과거 데이터가 남을수있어서 커밋 완료하고 올려야한다 트렌젝션 성질에 따라 남는것이 좋을때도 있고 나쁠수도 있음 레디스의 갱신을 놓치면 db 를 기준으로 재정렬한다
*(막히면: ADR-035. rate limit에선 같은 성질이 왜 '약'이었는지 대비하면 만점)*

### 4. 행동은 evict가, 시간은 TTL이 — 요약 캐시의 역할 분담

> 시작 문장: "학습하면 캐시를 지우는데도 TTL 5분이 필요한 이유는 dueCount 때문이다. dueCount는..."
> ✍️ (+ TTL 값 정하는 원칙 한 문장: "TTL은 이 데이터가 ___ 최대 시간")
dueCount는 사용자가 아무 행동을 하지 않아도 카드의 nextReviewAt이 지나면 증가하므로 캐시 삭제 이벤트가 발생하지 않는다.
> 문제가 생겨도 최대로 허용하는 시간이 ttl 이었어 그 시간이 지나면 데이터 삭제하고 다시 계산 그러면 ttl 이 짧으면 최신데이터가 바로 오고 길면 오래된 데이터가 보이겠네 대신 db 의 부담이 갱신을 자주 하면 올라갈수있겠네 
*(막히면: ADR-036)*

### 5. fail-open — Redis가 죽으면 무슨 일이 일어나나

> 시작 문장: "Redis는 이번 주에 붙인 것이므로, 죽으면 전부 지난주 방식으로 후퇴한다..."
> ✍️ (3곳 각각 + rate limit만 다른 뉘앙스: 기능이 아니라 ___를 포기)
기존 정상이면 레디스를 사용하고 문제가 생기면 기존에 사용하던 방식인 db 방식으로 쭉 사용한다
> 로그인 rate limit은 짧은 시간에 비밀번호를 반복해서 시도하는 공격을 막는 요청 횟수 제한이다. 
> VocaMaster는 5분 동안 5회 실패하면 30분 잠그고, Redis로 여러 서버의 실패 횟수와 TTL을 함께 관리한다
>  근데  그 rate limit 를 포기하고, 랭킹·요약은 DB 방식으로 대체한다.
*(막히면: redis-conventions.md의 표)*

## 예상 면접 질문 (구두시험 5문 그대로 — 이번엔 안 보고)

> 8/15 3차 인출 원문을 면접 말투로 다듬은 것. **[보강]** 표시 = 원문에 없어서 채운 조각 (다음 인출 땐 이것도 자기 말로).

### Q1. Redis를 어디에 왜 썼나요? (사용처 3개, 각 한 문장)

세 곳에 썼습니다. 첫째, **로그인 실패 카운터** — 5분 안에 5번 실패하면 30분 잠그는 rate limit인데, 서버가 여러 대여도 하나의 카운터를 공유해야 해서 Redis에 두었습니다. 둘째, **인기 랭킹** — 좋아요·복사 점수순 정렬을 매번 DB에서 계산하지 않도록 Redis Sorted Set에 순서만 캐싱했습니다. 셋째, **오늘의 요약 캐시** — 현황판 숫자 4개를 5분 동안 보관해서 반복 집계 쿼리를 줄였습니다.

### Q2. 그거 HashMap이나 MySQL 인덱스로 되지 않나요?

둘 다 가능합니다. 하지만 HashMap은 서버마다 따로 세기 때문에, 서버가 2대면 공격 5회가 3회·2회로 나뉘어 어느 쪽도 5회를 못 잡고 뚫립니다. **여러 서버가 동시에 하나의 카운터를 보게 하는 것**이 Redis를 쓴 핵심입니다. **[보강]** 인기 정렬도 인덱스로 충분하지만, 비로그인 사용자까지 반복 조회하는 읽기 집중 경로라 그 부하를 DB 밖으로 분리하고 싶었고, 대신 실제 데이터와 권한 판단은 DB에 남겼습니다. **[보강·중요]** 원자적 UPDATE(`count = count + 1`)는 MySQL 쪽 copy_count·like_count에 쓴 것이고, Redis에서 같은 역할을 하는 명령이 **INCR**입니다 — 둘을 섞지 않도록.

### Q3. 캐시와 DB가 어긋나면 어떻게 하나요?

DB 커밋이 끝난 뒤에만 Redis 점수를 올립니다. 그래야 트랜잭션이 롤백됐을 때 Redis에 과거 데이터가 홀로 남지 않습니다. 그래도 놓치는 갱신이 있으면 TTL이 설정한 시간 뒤에 자동으로 삭제되고, 다음 조회가 DB 기준으로 새로 채워 넣습니다. **[보강]** 이걸 최종적 일관성이라고 부릅니다 — 잠깐 어긋나도 결국 원본과 같아집니다.

### Q4. TTL은 어떻게 정했나요?

TTL은 그 데이터가 틀린 채로 있어도 참을 수 있는 최대 시간으로 잡았습니다. 길게 잡으면 낡은 데이터가 보이는 대신 DB 부담이 낮아지고, 짧게 잡으면 새 데이터가 빨리 오지만 DB 부담이 커집니다. 요약 캐시는 5분으로 잡았습니다 — 5분 전 숫자를 봐도 사용자가 손해 보지 않는 값입니다.

### Q5. Redis 장애가 나면 서비스는 어떻게 되나요?

기존에 쓰던 DB 방식으로 돌아갑니다. 인기 정렬은 DB ORDER BY로, 요약은 집계 쿼리로 대체됩니다. 단 rate limit만은 후퇴할 DB 방식이 없어서 그 시간 동안 방어를 포기합니다 — 로그인 기능 자체를 막는 것보다 낫다고 판단한 트레이드오프이고, **[보강]** 그래서 Redis 다운 알림을 나중에 보완하기로 했습니다.
