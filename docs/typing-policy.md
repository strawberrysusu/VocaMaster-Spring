# Typing 모드 채점 정책 (ADR-026 결정 B → ADR-051 확장)

> 사용자/면접 답변용 명세. 코드를 보지 않아도 정책을 한눈에 알 수 있도록 정리.

## 1. 목적

타이핑 채점은 *너무 엄격하면* 사용자가 화나고 *너무 관대하면* 학습 의미가 사라진다. 그 사이 **중간 길**을 명시적으로 정의하고 모두 같은 기준으로 채점.

## 2. 현재 정책

> 2026-11-14 확장(ADR-051): ③의 후보 뽑기에 **괄호 설명·영어 품사 표시·①② 무시**, **`;` `/` `・` 구분자**, **물결표 무시**가 더해졌다. 예전 규칙으로 정답이던 입력은 그대로 정답이다(예전 쉼표 조각도 후보에 남긴다). 규칙 본체는 서버 `common/AnswerMatcher.java`, 듣기 모드 프론트는 `frontend/src/lib/answerMatch.ts` — 두 구현이 `src/test/resources/answer-match-cases.json` 같은 사례표로 검증된다.

사용자 입력과 정답을 다음 순서로 처리한 뒤 비교한다.

### ① 양 끝 공백 제거
```
"  사과  "  →  "사과"
"사과 "     →  "사과"
```
단어 *중간* 공백은 유지 (예: `"ice cream"` → `"ice cream"`). 단 연속 공백은 하나로 본다(`"눈에  띄다"` = `"눈에 띄다"`), 물결표 `~ ～ 〜`는 지우고 비교한다(`"에 달하다"` = `"~에 달하다"`).

**공백이란** (11/14, ADR-051 보완): 보통 공백·탭·줄바꿈에 더해 NBSP, 얇은 공백(U+2009), 전각 공백 같은 유니코드 공백까지 — 목록은 서버 `AnswerMatcher.SPACE`와 프론트 `answerMatch.ts`의 `SPACE` 한 곳씩에 똑같이 적혀 있다. 제로폭 공백(U+200B)·BOM(U+FEFF) 같은 폭 없는 글자는 아예 없는 것으로 본다. 언어마다 다른 `trim()`은 쓰지 않는다 — Java `trim()`은 U+0020 이하만, JS `trim()`은 유니코드 공백까지 지워서 같은 답이 타이핑(서버)과 듣기·온라인 시험(화면)에서 다르게 채점되던 차이를 없앴다.

### ② `equalsIgnoreCase()` — 대소문자 무시
```
"Apple" vs "apple"  →  정답
"APPLE" vs "apple"  →  정답
```

### ③ 쉼표 복수 정답 분리 (Quizlet 패턴)
정답 필드에 `,`로 구분된 후보 여러 개를 둘 수 있다. **하나라도 일치하면 정답.**
```
correct_answer = "사과, 능금"
사용자 "사과"  →  정답
사용자 "능금"  →  정답
사용자 "apple" →  오답
```

각 후보는 다시 `trim()` + `equalsIgnoreCase()` 적용 후 비교.

### ④ 설명·표기 기호 걷어내기 (2026-11-14, ADR-051)
③의 쉼표 조각에 더해, 아래를 걷어낸 조각도 후보로 넣는다.
```
괄호 안 설명 삭제 (겹괄호·전각 괄호 포함)   "멸사봉공 (사사로운 이익을 …)"  →  "멸사봉공"
영어 품사 표시는 구분자                   "n. 바닥, 아래 v. 근거를 두다"  →  "바닥" "아래" "근거를 두다"
①② … 는 구분자                           "①대우하다 ②발송하다"          →  "대우하다" "발송하다"
; ； / ／ ・ 도 구분자                     "따뜻하다; 다정하다"            →  "따뜻하다" "다정하다"
```
한국어 가운뎃점 `·`(U+00B7)은 구분자가 아니다("사람·화물"은 한 덩어리). 일본어 가운뎃점 `・`(U+30FB)만 표기 두 가지("尊ぶ・貴ぶ")를 나누는 데 쓴다.

## 4. 한계 (의도적 트레이드오프)

### 답 자체에 `,`가 포함되면 깨짐
정답 `"Hello, World"`는 `["Hello", "World"]`로 분리되어 둘 중 하나만 맞아도 정답 처리됨 — **현재 의도와 다른 결과**. 단어 단위 학습이 주된 사용처라 *드문 케이스*로 판단하고 미해결.

### 정규화는 *최소한*만
구두점(`.`, `?`, `!`), 한글 자모 분리(NFC/NFD), 띄어쓰기 오차 등은 *건드리지 않음*. 사용자가 *정확히 외운 것*을 확인하는 게 학습 가치이므로 과도한 관대는 피한다.

### 괄호 속 쉼표 조각은 여전히 후보 (뒤로 호환의 대가)
예전 쉼표 조각을 그대로 후보에 남기기 때문에, 괄호 설명 안에 쉼표가 있으면 그 조각(예: `"순서·등급에서 첫 번째. 거북·게의 등딱지"`)도 정답이 된다. 예전에 정답이던 입력을 오답으로 바꾸지 않는 쪽을 택했다.

### 과거 attempt 결과는 재채점 안 함
정책이 변경되어도 이미 저장된 `typing_questions.is_correct`는 그대로. 사후 변경 시 *과거 통계와 일관성 깨짐* 방지.

## 5. STRETCH — Levenshtein (오타 허용)

| 정책 | 채택 여부 | 사유 |
|---|---|---|
| 1~2 글자 오타 허용 (Levenshtein 거리) | ❌ STRETCH | 정확 암기가 학습의 핵심. 오타 허용은 *틀린 철자*를 강화. 시간 남으면 *옵션 토글*로 도입 검토 |
