# 캐시 전략 — 인기 덱 랭킹 (Phase 5, ADR-035)

> 초안. Phase 7에서 측정 결과(히트율, 지연)로 보강한다.

## 원본과 사본

| | 주인 |
|---|---|
| 덱 내용·공개 여부·like/copy 카운트 | **MySQL** (유일한 진실) |
| 인기 **순서** (id 나열) | Redis ZSET `popular:decks` (사본 — 사라져도 재생성) |

**제1원칙: 캐시에 권한 판단을 맡기지 않는다.** Redis는 id와 순서만 주고, 응답을 만들 때 DB에서 `visibility = PUBLIC` 조건으로 다시 조회한다. 캐시가 아무리 낡아도 비공개 덱이 노출되는 사고는 구조적으로 불가능하다 — 최악의 경우는 "목록이 잠깐 성긴 것"뿐이다.

## 무효화(갱신) 이벤트 표

전부 **커밋 확정 후(afterCommit)**에만 실행 — 롤백된 트랜잭션의 흔적이 Redis에 남는 드리프트 방지.

| DB에서 일어난 일 | Redis에서 할 일 |
|---|---|
| 좋아요 | `ZINCRBY +5` |
| 좋아요 취소 | `ZINCRBY -5` |
| 남의 덱 복사 (카운트 대상) | `ZINCRBY +3` |
| PUBLIC → PRIVATE/UNLISTED | `ZREM` |
| PRIVATE/UNLISTED → PUBLIC | 현재 DB 카운트 점수로 `ZADD` |
| 덱 삭제 | `ZREM` |

증감(`ZINCRBY`/`ZADD`)은 **ready 표지가 있을 때만** 실행한다 (아래).

## 일관성: 이벤트 갱신 + TTL 재구축의 조합

- **이벤트 갱신** — 위 표. 즉시성 담당
- **TTL 재구축** — 놓친 이벤트(afterCommit 직후 서버 다운 등)가 있어도, 표지가 만료되면 다음 조회가 DB 기준으로 전체를 다시 만든다. **최종적 일관성**: 잠깐 어긋날 수 있지만 최대 1시간 안에 원본과 다시 같아진다

## ready 표지 + TTL 시차 (핵심 방어)

```
popular:decks        (본체)   TTL 65분
popular:decks:ready  (표지)   TTL 60분   ← 항상 먼저 죽는다
```

표지가 없으면 증감을 건너뛰고, 다음 조회가 재구축한다. **시차가 없으면**: 본체가 만료된 직후 좋아요 한 건이 `ZINCRBY`로 "덱 하나짜리·TTL 없는" 가짜 전체 순위표를 만들고, 키가 존재하니 재구축도 영영 안 걸린다. 표지를 먼저 죽여 증감을 멈춘 **뒤에** 본체가 사라지게 해서 이 레이스를 구조적으로 없앴다.

## 낡은 id(stale) 처리 — 자가 치유

조회 시 캐시가 준 id 중 일부가 DB의 PUBLIC 재검증에서 탈락하면 (비공개 전환·삭제 직후):

1. 탈락 id를 `ZREM` (자가 치유)
2. **이번 요청은 DB 경로로** — 20개 요청에 17개만 주는 페이지 구멍 방지

`totalElements`도 `ZCARD` 대신 DB `count`를 쓴다 — 캐시로 아끼려는 비용은 정렬이지 개수가 아니다.

## 장애 시 (fail-open)

Redis 예외는 전부 잡아서 경고 로그 + **DB 정렬 경로로 대체**. afterCommit 안의 실패도 삼킨다 — DB가 이미 성공했는데 Redis 때문에 500이 나가면 사용자가 재시도해 중복(복사 2번 등)이 생긴다.

## 캐시가 답하지 않는 질문

`keyword` 검색이 붙으면 무조건 DB 경로 — ZSET은 제목을 모른다. 키워드별 캐시 키는 조합 폭발 + 히트율 붕괴라 만들지 않는다. **캐시는 좁고 뜨거운 질문 하나(전체 인기 목록)만 맡는다.**

## 알려진 한계

- 재구축이 동시에 두 번 겹치면 마지막이 이긴다 — 같은 DB를 읽으므로 결과 동일(멱등), 분산 락은 과설계로 판단
- 자정 스코어 재계산 스케줄러(SHOULD)는 TTL 재구축이 역할을 흡수 — 필요성 소멸로 미구현
- 좋아요 취소가 재구축 직후 몰리면 순간 점수가 음수일 수 있음 — 표시엔 무해 (순서만 쓰므로)
